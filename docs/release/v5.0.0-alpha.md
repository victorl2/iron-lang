# Iron v5.0.0-alpha: One Debugger Everywhere, and 22 Bugs Fuzzed Out

A major alpha. Debugging now works the same way on Linux, macOS and Windows and in VS Code, Neovim and Zed: one adapter, `iron dap`, with Iron names and values, Iron expressions and conditions, Step Into that stays in Iron code, and panics that stop on the Iron line. Four new program fuzzers found 22 bugs (wrong values, use after free, double frees, leaks, rejected programs), all fixed. The language gains one rule (a list passed twice to a call with a `var` parameter is rejected, E0328), and the editor now reports the same strict errors as `ironc check`. This is an **alpha** release; the surface may change before GA.

**Upgrading.** Editors accept `ironls` 5.x: update the VS Code, Zed and Neovim integrations together with Iron. Programs that pass one list both to a `var` parameter and to another parameter of the same call need a copy (`grow(xs, xs.copy())`); the error says exactly where and how.

## Debugging

- **Windows through `iron dap`.** With LLVM's Windows release (`winget install LLVM.LLVM`, which ships lldb-dap) and Python 3.10 or later, Windows debugging goes through the same adapter as Linux and macOS, so it gets Iron names in the call stack, hidden temporaries, Iron expressions, conditions, logpoints, Step Into filtering and panic stops. The VS Code setting `iron.debug.windowsDebugger` (`auto`, `iron-dap`, `cppvsdbg`) chooses; `auto` falls back to the Visual Studio debugger when lldb-dap or Python is missing.
- **Panics stop on the Iron line in every debugger.** In `--debug` builds a failing check (assert, index out of bounds, null unwrap, division by zero, missing map key, ...) runs a debug trap in the Iron function when a debugger is attached, so gdb, LLDB and the Visual Studio debugger stop on the exact line with its locals, and the exception widget shows the panic message. Without a debugger nothing changes. Panics inside the runtime still go through `abort()`, where `iron dap` and the VS Code fallback select the Iron frame.
- **No compiler temporaries in Locals**, in any debugger: `--debug` builds mark them `nodebug` (`IRON_DEBUG_TEMPORARIES=1` keeps them for compiler work).
- **Iron expressions read variables captured by a closure** (`count + 1` inside or outside the closure).
- **`iron debug --check`** (and `iron dap --check`) says which debugger, Python and lldb-dap were found and how to install what is missing on this OS; editors show the same guidance instead of "adapter exited".
- `--debug` builds are reproducible: a tuple temporary's name was read from a dead stack buffer (a stack use after return in ironc).

## Editors

- **ironls**: no duplicate diagnostics in editors that pull them (VS Code, Neovim, Zed); the editor reports the same strict errors as `ironc check` (E0260 to E0264); document symbols, outline ranges and folding are right.
- **Zed**: the gutter run buttons offer Debug for `main` and for each test block; test names arrive without their quotes.
- **VS Code**: Toggle Line Comment writes `--` (it wrote `//`, which is not an Iron comment); Run and Run Test work in PowerShell; the packaging tool is up to date (`npm audit` clean).
- `iron` started through a symlink finds `ironc`.

## Fixes found by fuzzing

New program fuzzers (`tests/fuzz/prog_fuzz.py`: control flow, collections, objects and ownership, closures) compare each generated program against a model of the manual and run it under valgrind or ASan. They ran about 21,000 programs and found:

- **Wrong values:** a global written by a called function read back stale; a global stored in one match arm truncated to 8 bits; a recursive function with an enum argument matching the wrong variant (an LLVM tail recursion elimination bug, worked around).
- **Memory errors:** a closure capture in a loop freed twice; returning a parameter releasing its rc fields twice; `pad_left` / `pad_right` double free; a string built only to be compared leaking; a closure that replaces the variable holding it freeing itself; a `val` interface binding copying an object bytewise; one list passed to a `var` parameter and to another parameter (now E0328).
- **Programs that were rejected or failed to compile:** exhaustive matches with a bare unit variant arm, interpolation inside nested string literals, capturing lambdas in unreachable code, `weak rc null` and `heap` bindings in branches and loops, methods on elements of a list of rc handles, closure captures of enum payloads and of vars passed to `var` parameters, locals shadowing functions or captures, `len()` of a list of interfaces, and allocations declared at function entry.

## Language

- **E0328 for a list passed twice:** a call may not pass the same list (or map, or set) both to a `var` parameter and to another parameter, since growing it through the `var` parameter can move the elements the other one reads (manual 6.8). The error names the function, both parameters and the call to write instead.

## Tooling

- CI's ASan legs detect stack use after return.
- The runtime's worker pool starts on first use, so programs that do not spawn stay single threaded (and work around an LLDB on Windows crash with idle threads).

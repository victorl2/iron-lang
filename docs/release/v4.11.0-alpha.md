# Iron v4.11.0-alpha: Debugging in Every Editor

Debugging Iron programs now works from VS Code, Neovim and Zed through one adapter, `iron dap`, with Iron names and values for every kind of variable and a stop on the line that panicked. Editing got completion, signature help, references and rename inside function bodies, and a differential fuzzer found and fixed four miscompiles in expressions. This is an **alpha** release; the surface may change before GA.

## Debugging

- **`iron dap`** is a debug adapter any DAP editor can run. It builds a `.iron` file or package with `--debug`, starts lldb-dap (or gdb 14 and later) with the Iron formatters loaded, hides compiler temporaries and shows Iron function names.
- **VS Code:** an `iron` debug type, so F5 on a `.iron` file builds and debugs it. On Windows it hands off to the C/C++ extension's Visual Studio debugger.
- **Neovim and Zed:** an nvim-dap configuration and a Zed debug adapter, both using `iron dap`.
- **Break on panic:** a failed `assert` or any other panic stops at the Iron line that panicked, shown as an exception with the panic message.
- **Values:** enums (`Ok(5)`), interface values, `rc` and `weak rc` with their counts, rc lists and closures (function, line and captures) print as Iron values in gdb and LLDB, next to strings, lists, maps, sets and `T?`.
- **Names:** a variable captured by a closure shows under its Iron name, and a `locals` command lists only Iron bindings.
- **Stepping** into a loop no longer goes back to the function's first line.

## Editing

- **Completion** inside function bodies offers every name in scope (parameters, bindings, `for` and match bindings, lambda parameters) with its type, the standard library and builtins; member completion works on `ps[0].` and shows element types for list, Map and Set methods.
- **Signature help** works while a call is being typed, inside lambdas, interpolation, list literals and match arms, for builtins, constructors and calls through a function value.
- **References and rename** cover fields, methods, enum variants, type names and every binding in a body; renaming a standard library name is refused.
- **Inlay hints** have settings (`parameterNames`, `bindingTypes`) that apply without a restart, and show parameter names on constructions.

## Fixes

- Four expressions compiled to the wrong value:
  - `not (b == 1)` and other negated comparisons;
  - a comparison of comparisons, `(a == 6) != (b == 3)`;
  - 8 and 16 bit arithmetic used inside a larger expression, which did not wrap (`(a + a) < 0` with `a = 100: Int8`);
  - a `match` arm with a negative or constant pattern (`-5`, `1 << 3`), which never matched.
- An enum with explicit values (`SPACE = 32`) was its position at run time: `{e}` printed the wrong variant and the raylib bindings passed positions to C.
- An arena object whose fields own memory (String, lists, maps, rc) warns (W0605), since an arena never runs drops.
- Indexing a Map, a Set or any other value that is not a list, array or String is reported (`m[k] = v` reached the C compiler); the help names `get` / `put`.

## Diagnostics

- `&&`, `||` and `!` say to write `and`, `or`, `not`.
- A constant expression takes its partner's type like a literal does (`a + (2 + 3)` with `a: Int8`), and one that does not fit is reported with its value.
- An unsupported construct in a comptime function names what it is (`method calls are not available at compile time ('.push()')`) and what compile-time evaluation covers.

## Tooling

- `tests/fuzz/expr_fuzz.py` compiles random expressions over every integer width and compares them with a model of Iron's semantics; a ctest runs a fixed seed matrix.

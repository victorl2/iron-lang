# DROP-LAYOUT.md — Iron Resource Types ABI Lock

**Phase 24 ABI lock.** This document records the wire-stable layout of all
destructor (`_drop`) and copy (`_copy`) dispatch functions generated by the
Iron compiler for objects with `drop { ... }` or `nocopy` blocks. Downstream
consumers (Phase 26 rc vtable polymorphic drop, Phase 32 full `defer`
semantics, Phase 33 stdlib container rewrite, future debugger formatters)
depend on the invariants documented here.

---

## Overview

Every Iron object type `T` that declares a `drop { ... }` block in its
Iron source receives a static-dispatch C function `<TypeName>_drop(T *self)`
in the generated output. Every Iron object type that does NOT declare
`nocopy` and DOES declare a `drop { ... }` block receives a shallow
memberwise `<TypeName>_copy(T *dest, const T *src)` helper used for
copy-assignment (Phase 33 explicit `clone() -> T?` replaces this default
for fallible copies).

---

## 1. Destructor signature: `<TypeName>_drop`

### C function shape

```c
static void <TypeName>_drop(<TypeName> *self);
```

Where `<TypeName>` is the C-mangled Iron object name (spaces replaced with
`_`; all-ASCII identifiers only in v3.0-alpha.1).

### Semantics

1. The function is called exactly once on each object instance immediately
   before the instance's storage is reclaimed:
   - **Stack-allocated objects**: at scope exit, in reverse declaration order
     (LIFO). The `emit_defer_cleanup` path in `src/lir/emit_c.c` enqueues
     drop entries at alloca sites and emits them before every `return`.
   - **Heap-allocated objects**: at the `IRON_LIR_FREE` site in `emit_c.c`,
     immediately before `iron_heap_free`. The `/* PHASE-24 HOOK */` comment
     stub (landed Plan 21-01) was replaced by a direct `<T>_drop(&val)`
     call in Plan 24-02.
   - **rc-allocated objects**: deferred to Phase 26 (`PHASE-26 HOOK` comment
     stubs in `emit_c.c` + `emit_helpers.c` mark the insertion points). When
     Phase 26 lands, the vtable pointer on the rc header's `type_info` entry
     will call `<TypeName>_drop` as the last step before `iron_rc_release`
     frees the allocation.

2. The function body executes the user-written `drop { ... }` block
   verbatim, then drops each field that itself has a destructor in
   **reverse declaration order** (LIFO — deepest field last, matching
   RAII expectations).

3. Recursive drop calls on fields are emitted by `emit_helpers.c`
   `emit_field_destructors` at the tail of the generated function body.

### Example

```iron
object Pair {
    val first: Handle
    val second: Handle
    drop {
        println("dropping Pair")
    }
}
```

Generated C (simplified):

```c
static void Pair_drop(Pair *self) {
    iron_in_destructor = true;          /* Phase 24 DROP-04 panic-trap */
    /* user drop body */
    printf("dropping Pair\n");
    /* field destructors — reverse declaration order */
    Handle_drop(&self->second);
    Handle_drop(&self->first);
    iron_in_destructor = false;
}
```

---

## 2. Field destructor emission order

Field destructors are emitted in **reverse declaration order**: the last
declared field's destructor runs first, the first declared field's
destructor runs last. This mirrors C++ RAII destruction and ensures that
if `second.drop` observes state in `first`, `first` has not yet been
destroyed.

| Declaration order | Destruction order |
|-------------------|-------------------|
| field_0 (first)   | last              |
| field_1           | ...               |
| field_N (last)    | first             |

The user-written `drop { ... }` body runs BEFORE any field destructors.
This gives the user-written body access to all fields in their initialized
state.

## 3. Copy helper signature: `<TypeName>_copy`

### C function shape

```c
static void <TypeName>_copy(<TypeName> *dest, const <TypeName> *src);
```

### Semantics

Generated only for objects that are NOT `nocopy`. The default copy is a
**shallow memberwise copy**: each field is assigned via `=` from `src` to
`dest`. For fields that are themselves objects with copy helpers, the field
helper is called recursively.

Phase 33 ships `clone() -> T?` for fallible deep copies; the current
shallow-memberwise default is intentional for value-type semantics.

**Drop-07 panicking copy:** If a user-supplied copy body panics (via
`iron_in_destructor`-like mechanism — future work), the destination is in
an undefined state. This is documented UB. The fix is to not panic in a
copy body; types needing fallible copy should expose `clone() -> T?`
(Phase 33). See section 7 below.

## 4. Partial-init cleanup: `IronInitCleanupEntry` TLS stack

When an object's `init` method panics mid-initialization, any fields that
were already initialized must be dropped to prevent resource leaks.

### TLS types and declarations

```c
typedef struct IronInitCleanupEntry {
    void (*drop_fn)(void *);
    void *field_ptr;
    struct IronInitCleanupEntry *prev;
} IronInitCleanupEntry;

extern _Thread_local IronInitCleanupEntry *iron_init_cleanup_top;
```

### Register function

```c
void iron_init_cleanup_register(IronInitCleanupEntry *entry,
                                 void (*drop_fn)(void *),
                                 void *field_ptr);
```

Called from generated init-body C immediately after each field assignment
(`IRON_LIR_SET_FIELD` in an init-method LIR body). Pushes `entry` onto the
TLS `iron_init_cleanup_top` linked list:

```c
entry->drop_fn = drop_fn;
entry->field_ptr = field_ptr;
entry->prev = iron_init_cleanup_top;
iron_init_cleanup_top = entry;
```

The `IronInitCleanupEntry` structs are stack-allocated in the generated
init function; no heap allocation is required.

### Run-and-clear function

```c
void iron_init_cleanup_run_and_clear(void);
```

Called from `iron_panic.c`'s panic path when a panic fires while
`iron_init_cleanup_top != NULL` (indicating a panic-mid-init context). Walks
the TLS linked list in LIFO order, calling `entry->drop_fn(entry->field_ptr)`
for each registered field, then unconditionally resets
`iron_init_cleanup_top = NULL` (Pitfall 5: always reset to avoid stale
entries leaking across test harness runs).

### Limitation in v3.0-alpha.1

Iron's compiler always inlines `init` method calls as compound literals
(`Multi(true)` → `(Iron_Multi){.first = true}`), making the `multi_init`
C function dead code. The `iron_init_cleanup_register` machinery is
correctly emitted in the LIR body of `*_init` functions but is not
exercised end-to-end by the current corpus. Full panic-mid-init coverage
requires either:

- A compiler change to emit init calls as real function calls (not compound
  literals) for objects with complex init bodies, OR
- A Phase 32 `defer` integration that instruments the partial-init path
  explicitly.

This limitation is documented here. The `iron_init_cleanup_register` and
`iron_init_cleanup_run_and_clear` functions are compiled and linked into
every generated binary, ready for Phase 32 consumption.

## 5. Panic-trap: `iron_in_destructor` TLS flag (DROP-04)

### Purpose

When a drop body calls any function that panics (e.g., `iron_panic_bvec_oob`
on out-of-bounds BVec access inside a `drop { ... }` block), the panic must
be converted to a process abort with a specific message — panicking while
unwinding a destructor is undefined behavior (matches C++ `std::terminate`
semantics).

### TLS flag declaration

```c
extern _Thread_local bool iron_in_destructor;
extern _Thread_local const char *iron_current_dropping_type;
```

### Codegen pattern

The compiler sets `iron_in_destructor = true` in the **prologue** of every
generated `<TypeName>_drop` function (detected in `emit_func_body` by
checking if `fn->name` ends with `_drop`), and clears it in the epilogue
before each `return`:

```c
static void Bomb_drop(Bomb *self) {
    iron_current_dropping_type = "Bomb";
    iron_in_destructor = true;          /* prologue */
    /* ... drop body ... */
    iron_in_destructor = false;         /* epilogue (before return) */
}
```

### Panic intercept

Every existing `iron_panic_*` function (`iron_panic_bvec_oob`,
`iron_panic_stale_pointer`, `iron_oom_abort`, etc.) checks
`iron_in_destructor` at the top of its body:

```c
if (iron_in_destructor) {
    iron_panic_destructor_aborted(iron_current_dropping_type,
                                  __FILE__, __LINE__);
    /* noreturn */
}
```

### `iron_panic_destructor_aborted` output

Text channel (default):

```
iron: destructor panicked
  type: <TypeName>
  drop site: <file>:<line>
```

JSON channel (`IRON_PANIC_FORMAT=json`):

```json
{"panic":"destructor_aborted","type":"<TypeName>","drop_site":{"file":"<f>","line":<l>}}
```

The function calls `abort()` after printing; it is `__attribute__((noreturn))`
on GCC/Clang.

## 6. Nocopy enforcement

Objects declared `nocopy` in Iron source receive no `<TypeName>_copy`
function. The compiler emits `IRON_ERR_COPY_OF_NOCOPY_TYPE` (E0286) at
three enforcement sites:

1. `val b = a` where `a` has a nocopy type (VAL_DECL arm in typecheck.c)
2. Function parameter pass-by-value of a nocopy type (CALL arm)
3. `return` of a nocopy type by value (RETURN arm)

nocopy objects may only be moved by transferring ownership of the binding
(Phase 24 does not yet implement explicit move syntax; moves happen
implicitly at binding expiration via scope-exit drop).

## 7. DROP-07: panicking copy — documented UB

**Status: RESOLVED (Plan 24-03).**

A copy body that panics (either in user-written copy logic or in a field's
copy call) leaves the destination object in an undefined state:

- Fields assigned before the panic are initialized.
- Fields not yet assigned are uninitialized garbage.
- The source object has been partially read.

This is **documented undefined behavior** in v3.0-alpha.1. The compiler
enforces no special handling beyond the existing `iron_in_destructor`
panic-trap pattern (which applies to `drop`, not `copy`).

**Resolution:** Types needing fallible copy must expose an explicit
`clone() -> T?` method (Phase 33 Stdlib Container Rewrite). The compiler
will provide ergonomic guidance via a future diagnostic when it detects a
potentially-panicking operation in a copy body (Phase 33+ scope).

## 8. Phase 26 forward-reference: rc vtable polymorphic drop

The `IRON_LIR_RC_RELEASE` codegen path (Phase 26) will call
`<TypeName>_drop` through a vtable pointer stored in the rc allocation
header's `type_info` field. The vtable layout is:

```c
typedef struct IronTypeInfo {
    void (*drop_fn)(void *self);   /* Phase 26 — polymorphic drop */
    const char *type_name;
} IronTypeInfo;
```

`<TypeName>_drop` casts `self` from `void *` to `<TypeName> *`
internally. The `iron_in_destructor` prologue/epilogue pattern applies
equally to vtable-dispatched drops — the drop function itself sets and
clears the TLS flag, regardless of how it is invoked.

`PHASE-26 HOOK` comment stubs in `src/lir/emit_c.c` and
`src/lir/emit_helpers.c` mark the exact insertion points for Phase 26
vtable registration calls.

## Stability Commitment

The contract on this page is **stable** as of Phase 24. Any change to:

- `<TypeName>_drop(T *self)` or `<TypeName>_copy(T *dest, const T *src)`
  signatures
- `IronInitCleanupEntry` struct layout (field order, types)
- `iron_in_destructor` / `iron_current_dropping_type` TLS flag semantics
- `iron_panic_destructor_aborted` panic format substrings

requires an **explicit `IRON_VERSION_FULL` minor-or-major version bump**
plus a documented migration plan. Additional `#ifdef IRON_DEBUG_*`-gated
fields that preserve binary compatibility, comment edits, and refactoring
that leaves the tested substrings intact are permitted without a version bump.

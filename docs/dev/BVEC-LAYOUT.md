# BVEC-LAYOUT.md — Iron Bounded Vector ABI Lock

**Phase 23 ABI lock.** This document records the wire-stable layout of all
`Iron_BVec_T_N` types generated by the Iron compiler. Downstream consumers
(Phase 30 elision pass, Phase 33 `to_fixed`/`to_bounded` conversion helpers,
future debugger formatters) depend on the invariants documented here.

---

## Single-level bounded vector `[T; <=N]`

### C representation

```c
typedef struct { uint32_t len; T data[N]; } Iron_BVec_T_N;
```

Where `T` is the C mangling of the Iron element type and `N` is the
compile-time capacity bound. Name-mangling rule: spaces and `*` in `T` are
replaced with `_`. Examples:

| Iron type       | C typedef                         |
|-----------------|-----------------------------------|
| `[Int; <=4]`    | `Iron_BVec_int64_t_4`             |
| `[Float; <=8]`  | `Iron_BVec_double_8`              |
| `[Bool; <=2]`   | `Iron_BVec_bool_2`                |
| `[Point; <=16]` | `Iron_BVec_Iron_Point_16`         |

### Field layout

| Offset | Size         | Field  | Semantics                                  |
|--------|--------------|--------|--------------------------------------------|
| 0      | 4 bytes      | `len`  | Number of initialized elements (0..N)      |
| 4      | padding      | —      | Alignment padding if `alignof(T) > 4`      |
| —      | N * sizeof(T)| `data` | Inline element storage; indices 0..len-1 valid |

**Length field is `uint32_t`** (4 bytes, unsigned). Capped at 4 294 967 295,
well above any realistic compile-time `N`. Choice rationale: saves an
alignment slot vs `size_t` on 64-bit targets; N is compile-time-known so
a 32-bit cap is semantically sufficient.

### Alignment

```
alignof(Iron_BVec_T_N) = max(alignof(uint32_t), alignof(T))
                       = max(4, alignof(T))
```

For any T with `alignof(T) <= 4` (Int8, Int16, Int32, Bool, Float32) the
alignment is 4. For T = Int / Float / pointers (`alignof` = 8) the alignment
is 8.

### Programmer-visible sizeof

```
sizeof(Iron_BVec_T_N) = round_up_to_align(4 + N * sizeof(T), alignof(T))
```

Where `round_up_to_align(x, a) = (x + a - 1) & ~(a - 1)`.

Worked examples for `[Int; <=4]` (T = `int64_t`, sizeof=8, alignof=8):

```
sizeof = round_up(4 + 4*8, 8) = round_up(36, 8) = 40 bytes
```

For `[Bool; <=10]` (T = `bool`, sizeof=1, alignof=1):

```
sizeof = round_up(4 + 10*1, 1) = 14 bytes
```

### Zero-init (empty bounded vector)

A `var bv: [T; <=N]` declaration with no initializer emits:

```c
Iron_BVec_T_N bv = {0};
```

`len=0`, `data` zeroed. This is always a valid empty-bvec state.

### Push codegen

```c
/* bv.push(value) where bv: [T; <=N] */
if (bv.len >= (uint32_t)N)
    iron_panic_bvec_oob(__FILE__, __LINE__, (int64_t)bv.len, (int64_t)N);
bv.data[bv.len] = value;
bv.len += 1;
```

### Index codegen

```c
/* val x = bv[i] where bv: [T; <=N] */
if ((int64_t)i >= (int64_t)bv.len)
    iron_panic_bvec_oob(__FILE__, __LINE__, i, (int64_t)bv.len);
/* result = */ bv.data[i]
```

Index check fires when `i >= len` (past the initialized region), not when
`i >= N` (past capacity). This matches the Iron spec semantic: accessing an
uninitialized slot is an out-of-bounds error regardless of capacity.

## Nested bounded vector `[[T; <=N]; <=M]`

### C representation

The inner typedef is synthesized first (emit_ensure_bvec recursive case),
then the outer:

```c
/* inner */
typedef struct { uint32_t len; T data[N]; } Iron_BVec_T_N;

/* outer (elem type = Iron_BVec_T_N) */
typedef struct { uint32_t len; Iron_BVec_T_N data[M]; }
    Iron_BVec_Iron_BVec_T_N_M;
```

Example for `[[Int; <=4]; <=3]`:

```c
typedef struct { uint32_t len; int64_t data[4]; } Iron_BVec_int64_t_4;
typedef struct { uint32_t len; Iron_BVec_int64_t_4 data[3]; }
    Iron_BVec_Iron_BVec_int64_t_4_3;
```

### Storage

Total inline storage (no padding for illustration):

```
4 (outer len) + M * (4 (inner len) + N * sizeof(T))
```

For `[[Int; <=4]; <=3]`:

```
4 + 3 * (4 + 4 * 8) = 4 + 3 * 36 = 4 + 108 = 112 bytes (plus alignment padding)
```

Each inner bvec has its own independent `len` field tracking how many of
its N slots have been initialized. The outer `len` tracks how many of the
M inner bvecs have been pushed.

### Typedef emission order

`emit_ensure_bvec` guarantees the inner typedef is appended to
`ctx->struct_bodies` before the outer typedef. The recursive case:

```c
/* Inside emit_ensure_bvec(ctx, outer_ty): */
if (bvec_ty->array.elem->array.is_bounded)
    emit_ensure_bvec(ctx, bvec_ty->array.elem);  /* inner first */
/* then emit outer typedef */
```

## `List[[T; <=N]]`

### C representation

`List[[T; <=N]]` stores `Iron_BVec_T_N` elements by value on the heap.
The list struct is synthesized by `emit_mono_list_decls` after calling
`emit_ensure_bvec` to pre-declare the element typedef:

```c
typedef struct Iron_List_Iron_BVec_T_N {
    Iron_BVec_T_N *items;
    int64_t        count;
    int64_t        capacity;
} Iron_List_Iron_BVec_T_N;

IRON_LIST_DECL(Iron_BVec_T_N, Iron_BVec_T_N)
IRON_LIST_IMPL(Iron_BVec_T_N, Iron_BVec_T_N)
```

Each `push` copies the `Iron_BVec_T_N` struct by value into the heap
buffer (C struct-copy semantics). `get(i)` returns a copy.

### List storage size

```
heap allocation = count * sizeof(Iron_BVec_T_N)
```

For `List[[Int; <=4]]` with 3 elements:

```
3 * sizeof(Iron_BVec_int64_t_4) = 3 * 40 = 120 bytes
```

## Typedef emission order guarantee

The compiler ensures typedefs appear in `ctx->struct_bodies` in
dependency order before any function body references them:

1. Primitive and object struct typedefs (emit_type_decls)
2. Bounded vector typedefs via `emit_ensure_bvec` (called lazily from
   `emit_type_to_c` and explicitly from `emit_mono_list_decls`)
3. List-of-bvec struct typedefs via the OQ-10 extension in
   `emit_mono_list_decls` (after step 2 for the element type)
4. Function bodies (which reference the above types)

## ABI stability commitment

The `Iron_BVec_T_N` layout is **ABI-locked as of Phase 23**:

- `uint32_t len` at offset 0 — LOCKED
- `T data[N]` immediately after (with C alignment padding) — LOCKED
- Mangling rule: `Iron_BVec_<elem_c_mangled>_<N>` — LOCKED

Downstream consumers that depend on this layout:

- **Phase 30** — pointer-check elision pass may emit intrinsics that
  read `bv.len` directly; must match this layout.
- **Phase 33** — `to_fixed()` / `to_bounded()` conversion helpers
  memcpy from/to `Iron_BVec_T_N.data`; must match N and T.
- **Debugger formatters** — any future `iron-gdb.py` / `iron-lldb.py`
  pretty-printer must match `len` + `data` field names and offsets.

Changing this layout requires a Phase bump + an explicit ABI-break notice
in the changelog.
